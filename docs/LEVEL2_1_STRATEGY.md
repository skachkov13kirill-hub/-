# Финансовый Помощник — Level 2.1: UX-революция

## Результаты исследования рынка

### Почему люди бросают финансовые приложения

- **73% пользователей** бросают финтех-приложения в первую неделю
- **86%** бросают бюджет-приложения из-за ручного ввода (у нас этой проблемы нет!)
- **49%** установили приложение, но никогда не использовали — проблема онбординга
- **92%** новых пользователей становятся неактивными за 2 года

### Главные боли пользователей (из реальных отзывов)

1. **CoinKeeper** — деньги списываются после отписки, поддержка не отвечает, агрессивная реклама
2. **Дзен-мани** — неверная автокатегоризация, сломанная синхронизация, заброшенная веб-версия
3. **Monefy** — постоянная реклама, мало аналитики
4. **Mint (закрылся март 2024)** — синхронизация с банками ломалась, слабая поддержка
5. **YNAB** — требует высокой вовлечённости, сложен для новичков

### Что делают лучшие (чему учимся)

| Приложение | Сильная сторона | Что берём |
|------------|----------------|-----------|
| Copilot Money | Самый красивый UI + AI-чат | Уровень полировки интерфейса |
| Monarch Money | Надёжность + детектор подписок с уведомлением за 3 дня | Уведомления о подписках |
| Lunch Money | «Свежий ветер», простота, 90+ валют | Минимализм, время до результата |
| YNAB | Undo/Redo, методика zero-based | Система отмены действий |
| EveryDollar | Корзина для удалённых транзакций | Восстановление удалённого |
| Rocket Money | Split транзакций одним нажатием | Разбивка операций |
| Actual Budget | Полноценный split editor | Редактор разбивки |

### Тренды 2025-2026

1. **AI-ассистент** — от чат-ботов до автоматических сводок (90%+ точность категоризации)
2. **Автоматизация** — обнаружение подписок, напоминания, умные предложения
3. **Геймификация** — награды, бейджи, мотивация (у нас уже есть «Финансовое здоровье»!)
4. **Поведенческая психология** — не просто цифры, а изменение привычек
5. **Рынок растёт** — с $165.9 млрд (2025) до $207.69 млрд (2026), +25.2% CAGR

## Plan Level 2.1 — «Apple-quality UX»

Философия: каждая функция должна работать так, как если бы её делал Apple. Никакого усложнения — только интуитивная простота. Одно действие = один результат. Всё можно отменить.

### Задача 2.1.2: Undo/Redo — отмена любого действия

**Проблема:** Удалил операцию — всё, пропала навсегда. Изменил категорию — не вернёшь старую. Это катастрофа для доверия пользователя.

**Решение:** Трёхуровневая система безопасности.

**Уровень 1 — Toast с отменой (2 секунды):**
После любого деструктивного действия показываем toast с кнопкой «Отменить»:
```
┌─────────────────────────────────┐
│ Операция удалена    [ Отменить ] │
└─────────────────────────────────┘
```
- Операция ещё 5 секунд хранится в памяти (undoStack)
- Нажал «Отменить» → восстановлена мгновенно
- Не нажал → операция уходит в «Корзину»

**Уровень 2 — Корзина (30 дней):**
- STATE.trash = [] — массив удалённых операций с полем deletedAt
- В настройках: «Корзина (N)» — можно зайти, увидеть все удалённые, восстановить
- Автоочистка: при loadState() удалить из корзины записи старше 30 дней

**Уровень 3 — История изменений (для редактирования):**
- При изменении категории/описания/суммы — сохранять предыдущее значение
- tx.history = [{ field: 'category', from: 'Прочее', to: 'Продукты', date: '...' }]
- В модале редактирования: ссылка «История изменений» → список с возможностью откатить

**Как именно:**
```javascript
// Глобальный стек отмены
let undoStack = []; // максимум 10 последних действий

function performAction(action) {
  undoStack.push({
    type: action.type, // 'delete', 'edit', 'categorize', 'split'
    data: structuredClone(action.originalData),
    timestamp: Date.now()
  });
  // Выполнить действие...
  showUndoToast(action.description);
}

function undo() {
  const last = undoStack.pop();
  if (!last) return;
  // Восстановить в зависимости от типа...
}
```

**Возможные ошибки:**
- undoStack слишком большой → ограничить 10 записями
- Корзина переполняет localStorage → автоочистка 30 дней
- Пользователь нажимает undo после перехода на другой экран → toast должен быть глобальным

**Порядок действий:**
1. Добавить STATE.trash = [] и автоочистку в loadState()
2. Создать undoStack и функции undo()
3. Изменить deleteEditTx() → перемещение в корзину вместо удаления
4. Изменить toast() → добавить опциональную кнопку action
5. Добавить tx.history = [] для отслеживания изменений
6. Добавить экран «Корзина» в настройках
7. Добавить кнопку «Восстановить» для каждой записи в корзине

### Задача 2.1.3: Борьба с «Прочее» — умная перекатегоризация

**Проблема:** Огромное количество транзакций падает в «Прочее». Каждую нужно перекатегоризировать вручную, по одной. Это убивает UX.

**Решение:** Многоуровневый подход.

**Подход 1 — «Разобрать Прочее» (wizard после загрузки):**

После загрузки выписки, если в «Прочее» попало > 10 операций, показать карточку:

```
┌─────────────────────────────────────┐
│ ❓ 23 операции в категории «Прочее» │
│                                     │
│ Давайте быстро разберём:            │
│                                     │
│ Пятёрочка 15435 (×5)     [🛒 ▼]   │
│ OZON 04156 (×3)          [📦 ▼]   │
│ IP IVANOV (×7)           [❓ ▼]   │
│ АЗС ЛУКОЙЛ (×2)         [🚗 ▼]   │
│ ...ещё 6                           │
│                                     │
│ [ Применить ] [ Потом ]             │
└─────────────────────────────────────┘
```

- Группировка по мерчанту (первые 25 символов описания)
- Для каждой группы — dropdown с категориями
- Кнопка «Применить» — массово меняет категорию И создаёт правило
- Кнопка «Потом» — можно вернуться из настроек

**Подход 2 — Быстрый фильтр на экране операций:**

Добавить chip «❓ Прочее (23)» в фильтры. При нажатии:
- Показать только операции в категории «Прочее»
- У каждой операции — dropdown прямо в списке (без открытия модала)
- Свайп вправо → быстрый выбор категории

**Подход 3 — Предложения AI:**

При парсинге — если мерчант не найден в словаре, но содержит ключевые слова:
- «АЗС», «ГАЗПРОМ», «ЛУКОЙЛ», «SHELL» → предложить «Автомобиль»
- «АПТЕКА», «СТОМАТОЛОГ» → предложить «Здоровье»
- «ШКОЛА», «КУРСЫ», «UDEMY» → предложить «Образование»
Добавить 50+ fallback-правил для частых пропусков.

**Подход 4 — Скрыть/исключить из аналитики:**

На дашборде: возможность исключить ЛЮБУЮ категорию из расчётов:
```
Доходы: 182 500 ₽  Расходы: 156 300 ₽
[Все] [Без переводов] [⚙️ Настроить]
```
Кнопка «Настроить» → чекбоксы для каждой категории → сохранить как preset.

**Порядок действий:**
1. Добавить 50+ fallback-правил в categorizeTransaction()
2. Создать wizard «Разобрать Прочее» — показывать после загрузки
3. Добавить chip «Прочее (N)» в фильтры на экране операций
4. Добавить inline dropdown для быстрой перекатегоризации в списке
5. Добавить модал «Настроить фильтр» с чекбоксами категорий
6. Сохранять пресет фильтра в STATE.settings.dashExclude = []

### Задача 2.1.4: Split-транзакции — разбивка операции на категории

**Проблема:** Купил на заправке бензин + игрушку ребёнку = одна операция. Арендатор перевёл деньги = часть аренда, часть коммуналка. Нужно разбить.

**Решение:** Кнопка «Разбить» в модале редактирования операции.

**UX-флоу:**

```
Операция: АЗС ЛУКОЙЛ — 3 500 ₽

[ Изменить ] [ Разбить ] [ Удалить ]

        ↓ нажал «Разбить»

┌─────────────────────────────────────┐
│ Разбить операцию: 3 500 ₽          │
│                                     │
│ Часть 1:                            │
│ Сумма: [2 800 ₽]  Категория: [🚗▼] │
│                                     │
│ Часть 2:                            │
│ Сумма: [700 ₽]    Категория: [👶▼] │
│                                     │
│ Осталось: 0 ₽ ✅                    │
│                                     │
│ [ + Ещё часть ]                     │
│                                     │
│ [ Сохранить ]  [ Отмена ]           │
└─────────────────────────────────────┘
```

**Технические детали:**

Оригинальная операция получает поле splits:
```javascript
{
  id: 'sber_2025-01-15_...',
  description: 'АЗС ЛУКОЙЛ',
  amount: 3500,
  category: 'split', // специальная метка
  splits: [
    { category: 'Автомобиль', amount: 2800, description: 'Бензин' },
    { category: 'Дети', amount: 700, description: 'Игрушка' }
  ]
}
```

**Правила:**
- Сумма частей ОБЯЗАНА равняться оригинальной сумме
- Минимум 2 части
- Валидация: «Осталось: X ₽» — показывать в реальном времени
- Можно удалить разбивку (вернуть к одной категории)

**Влияние на расчёты:**
- В renderCategories() — если tx.splits, добавить каждую часть в свою категорию
- В renderDonut() — аналогично
- В renderAdvisor() — аналогично
- В export/CSV — строка «| АЗС ЛУКОЙЛ | 2 800 | Автомобиль |» и «| АЗС ЛУКОЙЛ | 700 | Дети |»

**Возможные ошибки:**
- Сумма частей не совпадает → кнопка «Сохранить» неактивна пока не совпадёт
- Пользователь ввёл 0 или отрицательное → валидация на вводе
- Редактирование split-транзакции → открывать сразу split-editor
- Удаление split-транзакции → удалить всю (со всеми частями)

**Порядок действий:**
1. Добавить поле splits в структуру транзакции
2. Создать UI split-editor (модал)
3. Добавить кнопку «Разбить» в модале редактирования
4. Обновить ВСЕ функции расчётов (renderCategories, renderDonut, renderAdvisor, catTotals)
5. Обновить export для корректного вывода split
6. Добавить возможность «Убрать разбивку» (вернуть к одной категории)

### Задача 2.1.7: Фильтрация межбанковских переводов

**Проблема:** Переводы между своими картами засоряют аналитику. autoMatchTransfers() существует, но не вызывается автоматически. Пользователь не видит, где его межбанковские переводы.

**Решение:**

**Автоматический запуск при загрузке:**

### Задача 2.1.8: Периодические переводы → авто-категория

**Проблема:** Арендатор переводит каждый месяц 35 000 ₽. Пользователь хочет, чтобы это автоматически попадало в категорию «Аренда», а не в «Переводы».

**Решение:** «Умные паттерны» — правила на основе суммы + отправителя + периодичности.

**Как работает:**

1. Система находит регулярные переводы (как findSubscriptions(), но для доходов тоже)
2. Предлагает: «Обнаружен регулярный перевод: Иванов И.А., ~35 000 ₽/мес. Создать правило?»
3. Пользователь выбирает категорию → правило сохраняется
4. Теперь каждый перевод от Иванов И.А. на ~35 000 ₽ автоматически = «Аренда»

**Структура правила:**
```javascript
STATE.smartPatterns = [
  {
    type: 'recurring-income',
    description: 'ИВАНОВ*',    // паттерн описания
    amountMin: 33000,           // ± 10%
    amountMax: 37000,
    category: 'Аренда квартир',
    createdAt: '2025-01-15'
  }
]
```

**Порядок действий:**
1. Расширить findSubscriptions() → findRecurringPatterns() для доходов и расходов
2. Добавить STATE.smartPatterns = []
3. После загрузки — показать предложения для новых паттернов
4. Применять smartPatterns при категоризации (приоритет между customRules и MERCHANT_RULES)
5. Показать в настройках рядом с обычными правилами

### Задача 2.1.9: Фильтр разрезов — исключение категорий из аналитики

**Проблема:** Пользователь хочет видеть «чистые» расходы — без переводов, без «Прочего», без ипотеки. Сейчас только фильтр переводов.

**Решение:** Расширенный фильтр с пресетами.

**UX:**
```
┌─────────────────────────────────────┐
│ ⚙️ Настроить отображение            │
│                                     │
│ Пресеты:                            │
│ [Всё] [Ежедневные] [Обязательные]  │
│                                     │
│ Исключить из аналитики:             │
│ ☐ Переводы                         │
│ ☐ Перевод себе                     │
│ ☐ Прочее                           │
│ ☐ Жильё/Ипотека                    │
│ ☐ Кредиты                          │
│ ☐ Коммуналка                       │
│                                     │
│ [ Применить ] [ Сбросить ]          │
└─────────────────────────────────────┘
```

**Пресеты:**
- «Всё» — без фильтра

- STATE.settings.dashExclude = [] (массив категорий для исключения)
- STATE.settings.dashPreset = 'all' | 'daily' | 'mandatory' | 'custom'
- applyDashFilter() → учитывать dashExclude
- Donut, categories, forecast — всё пересчитывается с учётом фильтра

**Порядок действий:**
1. Добавить STATE.settings.dashExclude и dashPreset
2. Создать модал «Настроить отображение» (вызов по кнопке ⚙️)
3. Добавить пресеты с предустановленными наборами
4. Обновить applyDashFilter() → использовать dashExclude
5. Пересчитывать все виджеты дашборда при изменении фильтра

## Что НЕ делаем в Level 2.1 (и почему)

- **IndexedDB** — localStorage хватает, усложнение не оправдано
- **Облачная синхронизация** — это Level 3, требует серверную часть
- **AI через API** — требует ключ и расходы, не для MVP
- **Push-уведомления** — требуют Service Worker, не критично
- **Графики трендов** — из Level 2, но уступает приоритету UX-задачам
- **Бюджеты по категориям** — из Level 2, перенести в Level 2.2
- **Шаринг картинкой** — из Level 2, перенести в Level 2.2
